# First workspace message slice — implementation brief

Status: implementation brief with bounded accepted increments tracked in the journey table below. The initial source-reuse/gap notes describe the design baseline, not current completion status. This is not acceptance of P1, the full checklist, or a release. The governing product baseline is `WORKSPACE_CHECKLIST_V3.md`; its delivery recovery table remains normative.

## Outcome and deliberate scope

Demonstrate a goal-directed loop with one local task and two authenticated simulated worker connections: goal -> bounded delegated work -> evidence -> next supervisor decision. Worker A sends bounded context to worker B. The supervisor sees it queued, explicitly authorizes B's next simulated turn, and sees the exact message included only in that turn. Restart and duplicate requests preserve logical identity and truthful delivery state. No provider calls, native-session attachment, live injection, dependency graph, automatic scheduling, or model-certification claim is part of this slice.

The goal remains visible while the bounded message/adapter lane runs. Give the task a supervisor-authored objective, acceptance criteria, active priority, lane ID/link and return condition. For example, the synthetic goal is to verify recipient-scoped delivery; the active lane is B's bounded verification; its return condition is a checked fixture receipt matching the selected context digest. A's prose and B's acknowledgement are advisory evidence inputs. Only the supervisor's typed, evidence-linked assessment can record that the declared criterion was met or choose the next lane. This is the smallest product framing that helps a conductor retain focus instead of becoming absorbed in transport details.

Use the existing local swarm coordinator as the sole task/claim/message-delivery authority. The workspace is a facade and projection. Keep conversation history, council recommendations and deliberation decisions in their existing typed kernels. Do not write a second authoritative message lifecycle into a room journal.

For the one-task message fixture, A is a registered context-producing participant and B owns the one execution claim. A does not need a simultaneous claim on the same task to send an authorized message. This respects the coordinator's existing one-live-claim-per-task rule. A's fixture can emit its message after a supervisor-supplied stimulus; it is not independent main-goal execution or a new billable attempt. Calling this fixture alone a conductor loop would overstate it. The separate, required conductor demo below assigns real simulated claims to both workers and completes two iterations under the same visible goal. Do not redesign coordinator task completion to simulate two concurrent owners.

## Required conductor demo: one goal, three bounded lane tasks

Choose separate lane tasks under one goal, rather than reuse a completed task or pretend multiple launches are one attempt. `SwarmCoordinator.create` already accepts several tasks; `_claim_common` permits one live claim per task, so A and B can work concurrently on different tasks. `_apply_terminal` ends a claim and sets the task terminal state. `_apply_release` merely releases a claim, does not establish a successful result, and does not prove cleanup or authorize another contact. `close` refuses active claims and unfinished tasks. Preserve all of those semantics.

Prepare three bounded task definitions in one workspace-enabled run: `main-1`, `side-1`, and `main-2`. Each links to one durable goal definition and has its own request binding, criterion/return condition and grant. Worker A executes the two main tasks in sequence; worker B executes the bounded secondary investigation. These are three separate simulated attempts, at most two concurrently active. They share no provider session or paid-attempt identity. The predeclared `main-2` task is not authorized to launch merely because it exists: require a fresh supervisor command after assessing iteration one. This small fixed demonstration needs no dependency graph engine or dynamic task insertion.

1. **Inspect and delegate, iteration one.** Show the unchanged goal, its criteria and active main priority. Explicitly grant A's `main-1` and B's `side-1` with different claim IDs and effect scopes. A completes a deterministic main-goal check and returns an evidence reference while B remains active on a bounded secondary issue. Verify A's substantive progress event/evidence happened while B's task was still active; merely displaying two worker names is insufficient.
2. **Check and choose, iteration one.** The supervisor validates A's fixture evidence and records a criterion assessment. B returns a bounded advisory finding, or is still pending at its declared checkpoint. The supervisor records whether that issue affects the critical path. In the normal demonstration it is nonblocking: retain its result/return condition visibly, then explicitly authorize `main-2` under unchanged or narrower scope. A fluent response alone cannot justify either the progress assessment or a new launch.
3. **Inspect and delegate, iteration two.** Re-inspect current goal, evidence, grants and lane status; admit A's distinct `main-2` claim. Include the selected B-to-A message only in this newly authorized attempt if it has arrived and fits. If it arrives after selection, leave it queued for a separate explicit disposition; do not modify the frozen turn. The cross-lane send grant must name the same goal/run, source and destination lane tasks and recipient instance; shared goal membership alone never grants all-to-all access.
4. **Check and choose, iteration two.** Validate `main-2` evidence, record met/unmet/unknown criteria, and choose the next decision: goal criteria satisfied, another bounded lane proposed, or blocked pending specific evidence. Complete `side-1` only when its actual investigation return condition is met; a noncritical recommendation can be explicitly deferred without creating or launching a new task. The success fixture finishes all three admitted tasks before run closure. Goal criteria met, outstanding delivery dispositions and run closed are separate displayed facts.

Critical-path rule: an issue that invalidates required evidence, shared scope safety, ownership or contact/spend certainty blocks the affected next grant; unrelated main work can continue only under a verified nonconflicting scope. A secondary lane does not become the main priority merely because it is noisy or slow. Record `continue_main`, `hold_affected_lane` or `promote_issue_to_priority` as a typed supervisor disposition with evidence/reason and the current goal revision. Keep unresolved side-lane work visible. Do not fabricate its completion to make the run close: an unfinished prepared task can leave the run open awaiting an explicit decision, consistent with current `close` behavior.

The demonstration's extra acceptance is therefore two complete inspect/delegate/evidence/next-decision iterations plus observed useful main work during side work. The one-task/two-worker message fixture remains the smaller protocol test; both are required before describing this increment as a goal-directed conductor slice.

## Smallest new implementation boundary

Proposed names below are interfaces to review, not claims that these functions exist.

1. `_workspace_protocol.py`: strict versioned message/grant/delivery/command validation and pure transition checks. Negotiate an explicit workspace feature version; preserve exact swarm/v1 validation. Avoid implementing all future entity behavior merely to define names.
2. `_workspace.py`: facade operations and bounded projections calling the existing coordinator mutation boundary. Extend `_swarm_coordinator.py` for authoritative events/replay. The facade has no scheduler, lease store or parallel write-ahead log.
3. `_workspace_worker_ipc.py`: supervisor-owned framed pipe connections, scoped capability admission, and simulated-worker adapter. No provider backend imports or generic shell-command execution. Real launches must use shared hidden-launch flags and existing verified process ownership/cleanup facilities.
4. `_workspace_content.py`: bounded immutable private context blobs. This is content storage, not an authority store. Store by supervisor-generated opaque reference, never a worker-supplied path. Journal content references/digests only; public projection omits raw references and bodies.

The first CLI/API projection can be plain structured task inspection. A full atlas redesign is not a prerequisite to proving this transaction. Before a user-facing preview ships, the checklist's minimal browser, accessibility, migration and release gates still apply.

## Authentication qualification

The achievable first qualification is **authenticated owned connections under a trusted OS-user model**. Supervisor starts two fixed fake executables, gives each only its dedicated inherited pipe handles, and exchanges a random challenge and scoped session key on that channel. Bind authenticated frames to instance, epoch, task, grant, monotonically checked connection sequence and payload digest. Exclude secrets from argv, URLs, logs, telemetry, context, the browser token and journal. Authenticate supervisor responses over the same channel. Limit handle inheritance; rotate keys on reconnection and revoke grants durably.

Names, process IDs, birth tokens, ACLs and an HMAC key readable by the same user do not isolate a hostile same-user executable. This slice must refuse a `hostile_same_user_worker_isolation` qualification. It tests hostile protocol inputs from a worker confined to its issued connection, with the OS user, launcher and supervisor trusted. The fake-worker result cannot justify launching arbitrary hostile code with access to supervisor memory/files. A later stronger claim needs verified OS isolation of process handles, memory, filesystem and credential access, with independent adversarial evidence.

Full supervisor restart closes connections and expires session keys. Reopen the durable store without launch, preserve queued bindings and report old instances disconnected. Replacement workers get new instance/epoch grants; pending old-instance deliveries hold until an explicit disposition creates a linked delivery for the selected replacement. A restart is not authority to transfer inboxes. A transport reconnect to an unchanged live instance is a separate future qualification unless a verified reconnect mechanism is included and tested.

## Transaction and truthful lifecycle

Start with one ordered A-to-B stream. Proposed message-fixture bounds: two workers, one task, one active execution claim, 32 pending messages, 4 KiB UTF-8 per message, at most eight complete messages per selection. The conductor demo extends only task/claim bounds to three predeclared lane tasks, two concurrent claims and three total simulated attempts, with one explicitly scoped B-to-A stream for the secondary finding. These are conservative fixture limits, not measured product promises. Count full encoded frame/context overhead and private blob retention separately. R13 determines whether admission can actually reserve these obligations.

Write and durably bind the immutable content blob before message acceptance. A blob orphaned before the journal commit is not an accepted message; cleanup is later bounded maintenance. An accepted reference missing or mismatching on replay holds/refuses execution. Do not manufacture its bytes from a redacted preview. No authoritative outbox mirror is needed: one admitted event creates the sender receipt and recipient queue projection.

`accepted -> queued -> included_in_attempt -> submission_started -> submitted -> acknowledged` uses the checklist's normative conditions. The first two facts may share one durable event. Freeze whole selected message IDs and compiled digest before submission; new arrivals remain queued. The adapter verifies the bytes actually written match the frozen digest. A held required predecessor pauses its stream. Record explicit included/deferred IDs rather than advancing a cursor past omissions.

In the fake adapter, `submission_started` precedes the first pipe write. `submitted` requires its documented full-frame receipt boundary; `acknowledged` requires a separately validated recipient receipt. An interrupted or partially written pipe yields `held_for_recovery`, not success and not automatic retry. Proven no write/contact can produce `not_submitted`; a new linked delivery still requires explicit disposition. Missing durable terminal evidence preserves uncertainty even if fixture logs suggest success. Message expiry/cancellation cannot erase a submitted attempt. Agent acknowledgements cannot complete task authority implicitly.

After the message fixture's B claim completes, do not reopen its completed coordinator task to manufacture a resumed chat turn. The conductor demo performs the second iteration through the distinct `main-2` task and a new authorized claim under the same goal. Real resumed chat wiring remains an additional increment following this contract and R02; the conductor demo establishes repeated goal-directed decisions without pretending to certify provider session continuity.
