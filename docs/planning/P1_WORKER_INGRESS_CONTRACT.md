# P1 worker-origin message ingress contract

Status: **base worker-send composite and bounded actual A-to-B ingress accepted**. The core had 141 independently verified runtime-independent cases; the later actual ingress/conductor gate passed 141 tests plus 53 subtests with 12 inspected files unchanged. This does not qualify native/provider adapters or the taskless supervisor endpoint. FABLE-SUPERVISOR-01 approved the additive direction with SI-01 through SI-07 conditions, which the lead adopted below before implementation.

This increment implements the atomic accepted-message/queued-delivery boundary required by `P1_VERTICAL_SLICE_BRIEF.md` and advances F17/F18. It adds no provider, scheduler, journal, native-session attachment or implicit launch.

## Connection and three authorities

The runtime derives the sender from the actual supervisor-issued authenticated `Channel` and its installed registry entry. Request JSON cannot supply a sender, worker epoch, authentication dictionary or capability. The registry binds the connection to workspace/run, source task, worker instance/epoch, current claim/attempt/lease generation and channel grant.

Keep these authorities distinct:

1. **Source execution/channel grant:** permits the current task-bound worker connection; it does not permit arbitrary cross-lane messages.
2. **Send scope:** explicitly permits `message.send` from that source to one named destination task and exact recipient instance/epoch within the same goal/run.
3. **Destination delivery grant:** remains the canonical message/delivery `grant_ref`; later turn admission independently validates execution permission, holds and current fences.

Shared goal membership grants no all-to-all permission. The first increment supports named task-bound worker recipients. An explicit typed supervisor endpoint remains a **required P1 follow-on**, not a native-adapter/P3 deferral. Supervisor inspection of ingress does not satisfy addressed supervisor messaging. Do not manufacture an executable dummy task or worker to fit the current schema. Message text remains context, never a vote, approval, permission, routing, model, account, spend or policy change.

## Worker request and response

Add worker-to-supervisor `message_send_request` and supervisor-to-worker `message_send_result` kinds to the existing authenticated framed transport. The strict request contains `schema`, `operation_key`, `destination_route`, `observed_grant_revision`, `content`, and optional `correlation_id`, `reply_to`, `causation_id`. Use schema `summon.workspace.message-send/v1`. Reject unknown fields and invalid primitive types. Content is UTF-8 data, never a path or command.

Preserve the current 4 KiB content and complete 8 KiB frame bounds, canonical digest, immutable channel binding, independent monotone directional sequences and bounded I/O deadlines. Allow at most one outstanding worker send request per channel initially. The existing pipe owner performs all reads and demultiplexes worker requests from the exact pending receipt/result sequence. No competing readers, unbounded request queue, receipt substitution or blocking reciprocal sends are permitted.

The response authenticates and correlates the operation/request digest plus the current request frame digest and wire sequence. A committed response reports message ID, delivery ID, stream sequence, committed revision and `delivery_state: queued`; it authorizes no execution. Refusals use bounded reason codes without exposing another recipient's content or existence details. An uncertain write/commit yields `indeterminate`, never a fabricated refusal or success.

## Composite schema and replay

Add nested event `workspace_message_sent` inside the existing `workspace_event` container. Preserve the existing common envelope: `event`, `protocol`, `workspace_id`, `run_id`, `operation_key`, `expected_revision`, `payload`. No second top-level journal format is needed.

The payload has exactly:

| Field | Binding |
| --- | --- |
| `message` | Existing canonical logical message; sender, recipient, tasks, IDs and stream sequence are constructed by the host. |
| `delivery` | Existing canonical initial delivery in `accepted` state; no parent, selection or inherited uncertainty. |
| `request` | Original `operation_key`, `request_sha256`, `destination_route`, `observed_grant_revision`, and the optional logical correlation fields. Correlation fields must equal those in `message`. |
| `source` | Existing canonical channel `binding` and full canonical existing `claim` snapshot, not a caller-authentication interface. |
| `send_scope` | `reference`, `revision`, `expires_at_ms`, `revoked`, `operation`, `goal_id`, `source_task_id`, `sender`, `channel_grant_ref`, `destination_task_id`, `recipient`, `delivery_grant_ref`. Exact operation is `message.send`; the verified source is a registered grant, and all scope fields must match the message/source. |

In this increment `destination_route` is exactly `send_scope.reference.id`. The send-scope and channel-grant references are registered with the source task; the destination delivery grant is registered with the destination task. Epoch currency comes from the runtime's installed channel/recipient registry, not an invented epoch field in the existing coordinator worker registry.

The outer observation time is captured by the coordinator. Historical structural replay uses that persisted time, never current wall-clock expiry. Live admission additionally verifies the installed channel and actual current grant source. Stored snapshots are audit claims from the trusted host, not self-authenticating capabilities.

One detached reducer operation validates the accepted pair using existing message/lane/grant/stream helpers, derives admission evidence, registers that evidence, derives the queued record and calls existing `validate_transition(accepted, queued, {durable_admission: reference})`. It then records the durable operation response and increments the workspace revision once. Reuse small canonical helpers; do not recursively replay synthetic events with artificial revisions. Existing `workspace_message_admitted` retains its accepted-only behavior.

The admission evidence digest is SHA-256 over the domain `summon.workspace.message-admission/v1`, a NUL separator, and the complete canonical nested event bytes. Its ID is deterministically derived from that digest. The reference is derived rather than included in its own source bytes, avoiding circular hashing. The evidence has category `event`, exact destination task/delivery binding, and consumed slot `settlement_for={delivery_id,target_state:queued,role:durable_admission}`.

The committed event is the evidence source; replay can reconstruct it. Candidate construction does not establish durability. Only successful append or replay of a committed record establishes admission. This evidence proves no provider contact, receipt, execution, cleanup or spend.

## Live coordinator seam

The dedicated method is `admit_worker_message(request, *, resolve_source, prepare_content)`. Callbacks are installed trusted runtime functions, never JSON fields. The runtime closes over an actual observed channel/request handle; a sender-shaped dictionary is insufficient. For a new operation, canonical read-only preflight uses the same validator as final admission to reject already-invalid routes/claims before publication. After that bounded authenticated preflight, invoke `prepare_content` **before acquiring the owner mutation**. It publishes/verifies the bounded immutable blob and returns its prepared descriptor and source binding; this preparation grants no permission to commit.

Within the existing `_mutation`, resolve the observed principal and stable command identity; return a matching prior committed result without admitting fresh work. For a new operation, capture time and validate current source claim/attempt/lease, cancellation, worker epoch, channel grant and explicit send scope. Resolve the exact destination grant/recipient, validate logical references, allocate IDs and sequence, reverify the immutable prepared descriptor/content binding, and append once through `_append_with_state`. Reply/causation parents must exist within the same endpoint pair, in either direction; unrelated-lane parent IDs are not accepted merely because they exist in the same workspace. Preflight never substitutes for this final same-state authorization.

`resolve_source(coordinator_state, workspace_state, request)` runs at most twice: once for read-only preflight and once for final same-state admission. It returns exactly `{binding, claim, send_scope}` with the shapes above. The runtime may pre-resolve/hash grant blobs into frozen facts; under mutation it checks those facts against current registered references and the actual installed observed channel/request without filesystem or pipe I/O. It must permit retrieval of a prior committed response without eagerly rejecting a now-expired claim; the base applies fresh lifecycle authorization only for new operations.

`prepare_content(request, content_id)` runs at most once, outside the owner mutation, and returns exactly `{ref, sha256, utf8_bytes}`. It handles at most one 4 KiB blob plus bounded metadata. The host derives `content_id` as `blob-` plus the first 32 lowercase hex characters of the full content digest, matching existing `ContentRef`. The publisher verifies the full digest and refuses a truncated-ID collision rather than overwriting. Use existing bounds of 16 lanes, 32 messages and 256 evidence entries; do not enumerate arbitrary directories or histories. Final descriptor verification is bounded against the trusted prepared immutable-content binding, not another worker-supplied descriptor. Any implementation requiring additional content lock/I/O inside the mutation must first specify its finite deadline and failure behavior; this draft does not authorize hiding such waits inside a callback. Callbacks must never wait for worker traffic, acquire a second coordinator mutation, launch a process, contact a network/provider or retry external work while holding the mutation. These are trusted-callback work limits, not a claim that arbitrary Python callbacks can be preempted safely.

Private immutable content is durable before acceptance; append failure can leave a bounded orphan, not an accepted message. A held lane remains held. Queued context cannot release a hold, change task lifecycle or start execution; later `admit_turn` remains independently governed.

## Idempotency, capacity and restart

Add a rebuildable send-operation index with at most `MAX_MESSAGES` (currently 32) entries, one per admitted message. Scope its key to the observed source principal/epoch and original operation key. The semantic digest includes content digest/length, destination route, observed send-grant revision and logical correlation fields. Exclude generated IDs, stream sequence, admission time, workspace revision and transport sequence. Replay verifies digest/message consistency.

A new authenticated frame with the same logical operation returns the same durable result without another append or reserve credit. Preflight checks existing operation identity before content preparation; deterministic immutable publication must not create another blob if an admission races with that check. Changed content/destination/correlation under that key refuses. An identical wire frame is still replay and revokes the channel. A duplicate response can be reconstructed before rechecking permission to admit new work; delivery of that response still requires an authorized observed connection. After full supervisor restart, old channels are revoked; replacement instances cannot silently inherit sender identity or retry authority. An authorized supervisor may inspect the recorded outcome.

The stored response is the original admission outcome at its original revision, not a current delivery-status projection. A later acknowledgement, hold or disposition cannot be rewound by displaying a duplicate admission response. The strict internal index value is `{request_sha256,response}`; response fields are `status`, `operation_key`, `request_sha256`, `message_id`, `delivery_id`, `stream_sequence`, `revision`, `delivery_state`, `execution_authorized`. Index/grant details are not exported by the public task view.

Reserve from the canonical queued candidate: the actual composite already includes one operation and its derived evidence entry. Charge its complete encoded wrapper and all remaining reachable transition/evidence slots, explicit effects-resolution budget and uncertainty tail. Do not charge a future queue transition, waive registry limits, preregister future receipts or consume unrelated settlement allowance. Preserve separate claim reserve. Close/status and fresh linked-delivery admission retain existing uncertainty rules.

## F17 boundary and qualification

Use a sibling `workspace` command family without changing legacy chat/swarm/council/deliberation or roster behavior. Worker-origin sends use the owned channel API. A host CLI send remains explicitly host-origin; there is no `--sender` impersonation. Typed private request-file/stdin input avoids argv prompt transport. Read-only projections can work independently; mutations require an authenticated active-host binding and otherwise return `workspace_host_unavailable` without provider fallback. No raw event append or credential-shaped JSON is a public command.

The coordinator/admission/state owner implements the composite and reserve/replay tests. The runtime/transport owner implements observed principal resolution, single-reader ingress and authenticated responses. The separate `workspace_worker_send_contract()` describes atomic base support and explicitly reports `authenticated_worker_ingress:false`; the existing ten-class ordinary contract remains unchanged. Generic runtime `record_event` must refuse the composite. The runtime coordinator subclass must delegate this composite to base replay so historical full claim/observation checks cannot be skipped. Activate runtime ingress only when the actual observed-source seam and focused gates pass.

P1 remains incomplete until the typed supervisor-endpoint follow-on lets an authenticated worker address the supervising principal under an explicit recipient grant. That follow-on must define durable endpoint identity, inbox/delivery semantics, correlation and acknowledgements independently of executable task selection. Test an actual worker-to-supervisor message, unauthorized supervisor impersonation, wrong-goal endpoint rejection, duplicate/restart behavior and unchanged permissions/priority/spend. Receiving an issue or suggestion cannot become an assessment, approval, vote or next-lane command automatically.

Decisive tests must include actual fixed processes: A authors context, only authorized B receives the exact queued content after separate turn admission, and no message launches or claims work. Cover lost-response logical retry; conflicting operation; forged sender and forbidden recipient; grant/epoch/claim changes under mutation; interleaved requests/receipts without deadlock; cross-channel/replayed/tampered frames; complete Unicode bounds; crashes before/after content and before/after append; restart revocation; historical persisted-time replay; and invalid derived/cross-delivery evidence. Exact-cap tests must admit the composite then complete real required settlement without extra capacity, and invalid branches must leave journal bytes unchanged. Preserve legacy CLI parsing and provider-inert refusal regressions.

## Lead-adopted P1 taskless supervisor endpoint — preliminary core implementation

Source constraint: `_workspace_protocol._message` requires destination task and worker fields; `_delivery` requires an executable attempt selection before receipt acknowledgement. `_workspace_state._admit_message` binds both endpoints to existing lanes. Reusing those records for a taskless supervisor would therefore fabricate a task/attempt or weaken an execution invariant. Current `_workspace_runtime.install_worker_ingress` and `_ingress_facts` can supply the observed worker principal, but their destination grant branch is deliberately task-bound.

**Recommended smallest additive change:** keep existing worker message/delivery records intact. Add explicit `supervisor_endpoint`, `supervisor_message` and `inbox_delivery` record variants in the same protocol module, coordinator journal and rebuildable projection. Extract only genuinely shared message/content/stream validation. This is an inbox delivery mode, not another store, scheduler or governance kernel.

- Endpoint: stable endpoint ID, workspace/run/goal, current owner instance/epoch, receiver grant and recovery-fence references, expiry and unbound/active/revoked/retired status. Admit one supervisor endpoint initially; cap ownership/grant revisions at 64. Its owner is an installed runtime consumer, not a fake coordinator worker or executable task. Endpoint epoch is distinct from the transient journal writer generation.
- Logical message: existing immutable message/content/correlation facts and real source task/worker, with an explicit supervisor recipient `{kind:supervisor_inbox,endpoint_id,owner_instance_id,epoch}` replacing destination task/worker fields only in this new record variant. The receipt record retains its own delivery ID and immutable recipient/grant binding. Keep logical message IDs and send-operation keys in shared bounded namespaces.
- Inbox delivery: `queued -> offered -> acknowledged`; queued/offered may enter `held_for_recovery`, queued may be explicitly cancelled/expired, and held may be dead-lettered. No rewind. A linked successor requires explicit fresh receiving authority and a new delivery ID. `offered` records a bounded offer ID, recipient epoch and exact content digest before exposure; acknowledgement means only `supervisor_context_received`. It proves no human/model understanding or approval. Track inbox exposure as `not_exposed`, `unknown` or `consumer_received`; disposition cannot erase uncertainty. Existing source task/provider effect facts remain untouched.

The three authorities remain source execution/channel grant, an explicit worker-to-supervisor send scope, and the endpoint's context-receiving grant. The third authorizes inbox consumption only. Add an explicit endpoint-scoped evidence subject, mutually exclusive with task scope, to the shared evidence registry; never attach endpoint grants to a dummy task. Existing task-scoped records remain valid and unchanged.

Use receiver-grant expiry as the endpoint's ownership deadline; do not create a separate heartbeat scheduler. Initial activation and replacement after explicit revocation are distinct trusted-host admissions under the existing coordinator mutation, with expected workspace revision and monotone endpoint revision. Replacement requires the next owner epoch, fresh verified grant and registered recovery fence; it cannot rewrite pending deliveries. There is no renewal command or hidden transfer. A stale owner cannot offer or acknowledge after expiry/replacement. Full host restart revokes old worker channels; recovery requires authorized endpoint reactivation. Old pending/offered deliveries retain their old owner binding and are held before any re-exposure; a new consumer cannot silently acknowledge or inherit them. Logical owner fencing makes no claim that an old process or provider was physically stopped.

The worker wire request can remain unchanged: its explicit authorized `destination_route` resolves to this typed supervisor send scope. Dispatch to a dedicated `admit_supervisor_message` path after source verification; do not coerce it through `admit_worker_message` or permit generic `record_event` to bypass ingress. Admission atomically stores immutable content reference, queued inbox delivery, journal-derived admission proof and the original idempotent response. Preserve the unchanged shared wire semantic digest and operation-key namespace. Only the supervisor event and journal-derived admission proof use distinct type/domain tags; changing destination mode cannot admit a second message under the same principal/key. Stream ordering includes source principal/task and exact endpoint owner epoch. Duplicate logical requests return the historical outcome; duplicate wire frames remain invalid.

Adopted host API: define, activate, revoke and retire an endpoint; inspect the bounded inbox; explicitly offer the next eligible message to the installed consumer; and record its correlated context receipt. Replacement is a new activation admission after revocation, with explicit linked-delivery recovery. No callback may wait for worker/model traffic under mutation. Read/prepare content outside the owner lock; validate its immutable binding and live receiver grant at the final boundary. Receiving text cannot invoke assessment, priority, policy, spend, council, deliberation or launch operations.

Capacity: preserve the existing combined 32-message/128-delivery limits, rather than adding 32 messages per recipient mode. At admission reserve every remaining finite offer/receipt/hold/disposition event and actual proof-registration slot, while retaining exposure uncertainty in the immutable lifecycle and final status. Endpoint updates use ordinary capacity; reserve required revocation/recovery bookkeeping separately when activating an endpoint. A full inbox refuses atomically. Closing requires an explicit finite disposition of pending inbox deliveries; task completion cannot refund them.

Decisive journey: an actual authenticated child computes a bounded issue message addressed to the supervisor route; the registered runtime consumer explicitly receives its exact content and records a correlated receipt, while the coordinator's task count/claims, priority, permissions and spend remain unchanged. Test wrong supervisor impersonation/goal/epoch, task-versus-endpoint grant substitution, expiry/replacement races, prefix ordering, lost-response retry, crash after offer before receipt, and explicit recovery to a fresh endpoint epoch that inherits prior unknown exposure, the predecessor offer ID and possible_duplicate. Recovery never promises absence of duplicate exposure. Exact-cap tests must permit the required later receipt or hold/disposition without borrowing task execution budget. An inbox receipt must never appear as a council vote, deliberation ballot or human approval.

**Considered alternative, not selected for this slice:** introduce a versioned generic destination union across all messages and delivery adapters now. It offers a cleaner eventual public address type, but changes the already-qualified A-to-B validators/runtime and requires a larger migration/requalification surface. Recommend the additive variants for this required P1 slice, with later address unification as a deliberate compatibility change. A supervisor-owned executable lane is not a valid alternative.

Ownership: protocol/core owner implements the strict variants, same-journal admission, fences, combined quotas and finite reserve; runtime/transport owner implements actual consumer identity and process verification while preserving A-to-B; presentation/CLI owner implements the bounded projection and explicit controls. The lead has authorized the bounded implementation. Contract readiness and synthetic core tests do not activate the feature or prove an actual consumer.

The exact adopted obligation table is:

| Event/action | Exact proof roles and categories | Obligation |
| --- | --- | --- |
| Initial accepted -> queued inbox admission | Derived `durable_admission:event` | New message and finite inbox settlement reserve |
| queued -> offered | `receiver_grant:grant`, `offer_intent:event` | Record intent before content exposure |
| offered -> acknowledged | `consumer_receipt:adapter_receipt` | Exact current offer/consumer receipt only |
| queued/offered -> held_for_recovery | `hold_observation:observation` | Preserve exposure; reserve explicit disposition |
| queued -> cancelled | `authorized_cancellation:grant` | Explicit context cancellation |
| queued -> expired | `expiry_observation:observation` | Affirmative expiry observation |
| held_for_recovery -> dead_lettered | `authenticated_disposition:event` | Finite disposition, retaining unknown exposure |
| Explicit linked successor | `fresh_receiving_grant:grant`, `recovery_fence:fence` | Fresh admission/budget, never parent rewind |
| Endpoint activation | `receiver_grant:grant`, `owner_fence:fence`; replacement also `recovery_fence:fence` | New bounded ownership admission |
| Endpoint revocation | `owner_revocation:fence` | Revoke current operational authority |
| Endpoint retirement | `recovery_fence:fence` | Explicit no-replacement disposition/new admission |

- **SI-01:** endpoint state is `unbound -> active -> revoked -> retired`, or revoked to a newly admitted higher epoch; no hidden renewal/transfer. Reserve required finite revocation/recovery proof slots and retirement path before activation, alongside each inbox's actual remaining event/proof slots. Every byte uses the existing complete encoded-wrapper bound. `inbox_deliveries` is separate from task deliveries, but their total is at most 128; both message variants share the existing 32-message and operation-key quotas. The 127-task-plus-one-inbox boundary must refuse a 129th delivery of either type without journal change.
- **SI-02:** evidence registration has exactly one subject, `task_id` XOR `endpoint_id`. Endpoint references must exist. Offer-intent and consumer-receipt evidence is additionally bound to the exact inbox delivery. Endpoint lookup cannot accept task-scoped grants, or vice versa.
- **SI-03:** immutable consumer binding is `{workspace_id,run_id,endpoint_id,owner_instance_id,epoch,receiver_grant_id,receiver_grant_sha256}`. The trusted callback closes over an actual installed consumer handle and supplies owner/epoch facts; command JSON cannot supply them as authority. Current endpoint and receiver grant are checked under the mutation. Historical operation readback still requires the authenticated original consumer binding; it is not a new receipt or a new owner's permission.
- **SI-04:** stale, expired or replaced consumers cannot add an accepted receipt. Offered exposure never returns to `not_exposed`. A successor retains `prior_offer_id`, `inherited_exposure:unknown` and `possible_duplicate:true` when applicable. There is no promise of recovery without duplicate exposure. Late observations require a future separate contract. A terminal inbox disposition may finish its finite obligation while retaining unknown exposure, but status/UI must label it disposed with unknown exposure, never clean/received/resolved. Independent source/provider uncertainty continues to block close.
- **SI-05:** this slice permits only forward parent links from the same source task/principal to the same supervisor endpoint. Task-message parents and reverse supervisor-send links are refused until a typed supervisor-send contract exists.
- **SI-06:** a new-epoch offer is blocked while any sender has old-epoch queued/offered deliveries at that same endpoint that have not been held/disposed. Unrelated endpoints do not participate in this fence; stream ordering remains source/stream/endpoint scoped. Validate an explicit registered recovery fence, not merely a fresh recipient name.
- **SI-07:** generic runtime `record_event` must refuse live inbox/endpoint ingress operations. A real local consumer receipt is tagged `receipt_kind:supervisor_context_received`, `consumer_kind:owned_fixed_supervisor_consumer/v1`, `qualification:simulated`. It establishes exact bytes received by that fixed consumer, never model/human understanding, context inclusion, vote, ballot or approval. A separate actual-process gate is mandatory.


### Preliminary core integration boundary

The pure/core increment now implements `_workspace_protocol` record variants and lineage checks, `_workspace_state.inbox_summary`, canonical admission helpers and the existing coordinator sole-writer methods. This is a trusted-host structural/journal boundary, not authentication of callback dictionaries. Actual consumer identity, source interpretation, generic-event bypass refusal and process recovery remain separate runtime qualification.

`admit_supervisor_message(request, resolve_source=..., prepare_content=...)` preserves the existing worker wire request, semantic digest, shared send index and queued response. `send_admission_evidence(event)` uses `summon.workspace.supervisor-message-admission/v1` only for the typed supervisor event; durable readback must reconstruct the exact committed event. `canonical_supervisor_send_event` is the shared structural validator.

`supervisor_inbox_command(command, resolve_consumer=...)` accepts `{operation_key,endpoint_id,expected_revision,action}` plus the action fields: activate adds `receiving_grant_ref`; offer adds `delivery_id`; receipt adds `delivery_id,offer_id`; hold/dispose/cancel/expire add `delivery_id,reason`; link adds `parent_delivery_id,new_delivery_id`. Define/revoke/retire add none. `expected_revision` is the workspace revision. The callback returns exactly `{consumer,evidence,receiver_grant_ref,lease_expires_at_ms,offer_id}`; an absent consumer has null grant/lease. Live actions require the actual installed original consumer at the runtime boundary, with matching current endpoint grant/lease checked under the owner. Independent host-authorized recovery may use a null consumer, never an inferred approval flag. The fixed response contains `{status,operation_key,revision,endpoint_id,delivery_id,offer_id,exposure,possible_duplicate,consumer_kind,qualification}` with null nonapplicable fields.

`supervisor_inbox_contract()` advertises the seven separate core classes: endpoint defined/activated/revoked/retired, supervisor message sent, inbox delivery advanced/linked. Its `consumer_authentication:false` explicitly prevents a core-only success from claiming an authenticated adapter. The existing ordinary ten-event capability remains unchanged.

Endpoint revisions have a structural settlement reserve as well as a byte reserve: active is at most 62, revoked at most 63, retired at most 64. A rejected fresh activation at revoked63 cannot prevent retirement64. Evidence slots use either `{delivery_id,target_state,role}` or endpoint-control `{endpoint_id,epoch,target_state,role}`; registrations use task XOR endpoint subjects. The complete encoded registration bound covers all three subject/slot shapes. Already registered exact slots receive no second reserve credit. Inbox disposition may release its finite context obligations while retained exposure remains unknown; task/provider obligations remain independent.

SI-01 test-scope refinement: the 127-task-plus-one-inbox fixture tests the pure shared-map guard, not an operational concurrency promise. A sequential single-successor recovery history needs delivery-bound hold and distinct-category disposition evidence for each replaced task attempt (126 of each before goal, grant and inbox evidence), reaching the independent 256-evidence limit first. No quota is raised and no fake admitted journal history is constructed to claim128 operational deliveries. Separate real-journal tests exhaust evidence plus reserved slots, refuse unrelated registration with unchanged bytes, then complete newly obtained offer/receipt/control evidence and close under the preserved reserve. Exact-byte-cap tests separately cover receipt and held/disposition branches.

`validate_inbox_lineage(parent,child)` checks immutable ancestry even after receipt progression, while `validate_inbox_link` separately checks initial queued state and required proof references. Presentation reuses lineage and `inbox_summary`; it must never manufacture a recovery proof to render a progressed child. Core fixtures are provider-inert synthetic callback evidence. Public/operator command reconciliation and actual restart recovery still require their own qualification.


The preliminary linked-recovery core fixtures pair real journal reopen tests with the separately qualified runtime consumer journey: queued and offered parents receive explicit hold/disposition, a new epoch has fresh receiving authority and registered recovery fencing, and the linked child retains the immutable logical message and parent offer/exposure history through its receipt. A separately measured link-admission byte cap covers remaining parent disposition, child cancellation and endpoint retirement; the earlier parent budget is never claimed to authorize a fresh child. Ordinary task-recipient retry still preserves its destination task and originally declared attempt budget.
