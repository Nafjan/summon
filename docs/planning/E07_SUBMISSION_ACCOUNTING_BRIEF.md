### Finite settlement producer contract (2026-09-09)

The workspace v2 accounting validator now admits a finite producer contract,
and the admission bound is generated from the same maxima and journal encoder
used by settlement. Accepted shapes are limited to a 16 MiB Summon-visible
estimate (with the declared ceiling of 4 MiB estimated tokens), six finite
usage metrics capped at 4 MiB each and at 18 canonical JSON characters (so
long finite float spellings cannot outrun the bound), an 80-character usage
provenance string, the observation scopes `unestablished`, `attempt_total`, or
`last_step_snapshot`, and the four typed contact-evidence values. Character
limits are measured against the JSON contract: the bound uses six-byte
control-character escapes rather than printable ASCII. The estimate scope,
boundary, and provider-outside-scope list are exact workspace values; attempt
kinds are capped at 64 characters, parent attempt IDs are 32 lowercase hex
characters, and owner generations at the signed 64-bit maximum. This keeps
the reservation finite without pretending to know provider-added context.

The provider-free capacity matrix now exercises not-submitted, submitted with
reported usage, submitted with missing usage, and indeterminate outcomes. It
uses escaped-string, long-float, non-null-parent, maximum-generation, and
maximum-timestamp shapes in the admission-bound probe, checks that the bound
fits the 8192-byte demo reservation, then settles through the real sole-writer
path with the runtime generation/timestamp and measures those frozen journal
bytes. It also confirms an exact duplicate does not append. The test does not
pretend that the live append itself uses synthetic maximum timestamps.
Values outside the finite contract are refused before append; Summon does not
round, clamp, zero, or silently discard the original private usage evidence,

### Accounting capacity and spend are separate lifecycles

| Actual boundary | Accounting capacity | Authority and uncertainty |
| --- | --- | --- |
| Atomic admission | Reserve bounded records/bytes for the selected claim and attempts. | No provider submission or extra spending authority is implied. |
| Budget consumed / launch intent | Keep the accounting reservation outstanding. | The existing one-use launch budget is consumed; do not refund or relaunch. |
| Submission or interruption | Preserve enough capacity to write the bounded accounting outcome. | Actual submission evidence controls classification; missing evidence stays unknown. |
| Typed accounting outcome durably appended | Release only the capacity for that retained outcome, through canonical replay. | The outcome may honestly report unknown contact/usage/spend. Existing uncertainty holds remain. |
| Exact duplicate outcome | Return the original result without another write or capacity release. | Changed attempt, owner, policy, selection or payload identity must refuse. |

Accounting settlement does not require learning an unknowable provider outcome.
A durably retained, correctly bound indeterminate outcome can settle its storage
obligation while spend/contact holds persist. This distinction avoids both early
capacity release and an unnecessary permanent storage reservation. Bound actual
encoded outcome size and record count before admitting work, and verify the
same transitions through the real writer and replay, including concurrent claims.

## Problem and intended behavior

Every physical submission must have its own accounting evidence. Reusing the
same logical message or compiled bytes does not make a later submission free.
Show scoped estimates separately from provider-reported usage and caching;
missing evidence remains unknown. A process launch is not proof of a remote
request, but possible contact must still retain uncertainty and budget holds.

The current typed compiler supports safe/off and labels its bytes/4 estimate.
That estimate covers its context fragment, not the complete provider input.
Workspace context is a separate path: it serializes 1–8 complete selected
messages into a bounded envelope, without summarization, deduplication or
diagnostic elision. Historical plan/v1 has no explicit context policy; additive
v2 policy declaration still needs runtime admission and settlement. These are
implementation gaps, not reasons to rerun the narrow usage-advisory suite.
