## Decision and evidence

Choose one encrypted browser-session draft record, with a dedicated host draft-retention secret and explicitly installed retention authority. Retain memory-only operation as an honest opt-out mode; it does not satisfy reload/restart preservation. Defer a mutable host draft store and text-free operation lookup to separate justified increments.

Two advice corrections matter. First, sharing a key across purposes was not demonstrated to be an exploitable vulnerability; choosing a separate retention secret is an architectural isolation decision. Second, one current browser session digest does not prove that the runtime has one stable operator principal. The new runtime explicitly binds `operator_id`. Keep the display label constant, but bind the actual stable host operator into recovery identity and key derivation without exposing it as a personal identity.

## Conditions for implementation

1. **Independent secret and authority.** Use a distinct host-held draft-retention secret, not the raw presentation key. Derive a per-scope key with a versioned purpose and canonical workspace/run/stable-operator/key-epoch binding. Neither host secret is returned to the browser. A separately installed compose/retention scope is required; a read bearer never installs it. Preserve both private host keys and their epochs deliberately for restart; changing retention secret must change its epoch. No automatic reconstruction from browser metadata.
2. **Bounded ciphertext.** Encrypt only the exact UTF-8 text bytes using platform AES-GCM, an explicit 128-bit tag and a fresh 96-bit random nonce for every seal. Put fixed metadata in authenticated associated data, not JSON-escaped text inside the ciphertext. At 2048 plaintext bytes, ciphertext plus tag needs 2752 base64 characters; the nonce needs 16. Use one ASCII serialized record capped at 4096 bytes/code units, with a fixed bounded AAD schema capped at 1024 bytes and an exact whole-record maximum test. Do not rely on Fable's approximate metadata arithmetic. Overflow refuses persistence/send without overwriting the previous record.
3. **Principal and context binding.** AAD must bind version, opaque workspace/run scope, opaque stable operator scope, opaque target, operation key or explicit unsent marker, draft state and key epoch. Display only Local operator; no personal identity claim or raw host operator identifier. Derivation uses the actual stable host principal, not a constant label. Never trust unauthenticated headers to change target, permission or scope; verify current authenticated scope and the tag before accepting restored content.
4. **One frozen pending send.** While unsent, edits may replace the one draft. Once sending begins, freeze text, target and operation key and lock composition until its outcome is reconciled. Do not keep a new editable draft over an older unknown send. Use version/generation checks and serialized or coalesced crypto work so an older async seal cannot overwrite a newer draft, a recorded result, a different target or a newly authenticated scope. A recorded queue response is admission evidence, not proof of current delivery or consumption.
5. **Unreadable and rotated records remain unresolved.** Malformed/oversized data, tag failure, incompatible scope or unavailable epoch must not be overwritten, retargeted or converted into a fresh send. Distinguish an observed epoch mismatch from generic authentication failure without trusting either as authority. Key/presentation rotation can leave recovery unavailable; keep the pending operation visibly unresolved. Do not promise recovery from lost secrets or corrupt ciphertext.
6. **Key endpoint.** Use authenticated POST with exact Origin/Host, JSON, bounded shape and no-store handling. Recheck current compose/retention authority around any blocking work. Refuse read-only surfaces and missing scope. Return only the derived key and bounded scope/epoch descriptors needed for recovery; never expose either host secret, a bearer, raw operator identity or private source. No GET/query-string key delivery, storage of keys/bearers in browser persistence, logging or public projection.
7. **Persist before contact; reconcile before replacement.** Seal, write, read-back verify, then submit the exact bounded request. Storage failure prevents submission. Restore only after fresh authentication and scope verification, and offer exact-key lookup before any explicit continuation. No automatic send, fresh key, retry, retarget or authority restoration. Clear the composer only on a matched durable queue result; clearing/storage failure must not hide a remaining unresolved operation.
8. **Wire limits, opt-out and honest lifetime.** Enforce both 2048 UTF-8 text bytes and 4096 encoded request bytes, including JSON escaping. A storable draft may still require editing before its request fits. State that default recovery is for this tab across reload and a restart retaining the same host keys; tab closure, storage policy and key loss are outside that promise. Memory-only/opt-out mode must disclose its limits. Explicit ciphertext discard must not turn an unresolved send into cancelled/not-sent; preserve minimal pending identity and uncertainty. No guaranteed erasure or protection against same-origin script, the trusted OS user, or combined host/browser storage access is claimed.

## Acceptance and falsification

The conductor must provide source/test evidence for:

- Separately authorized key endpoint; denied host/origin/bearer/read-only/scope cases; exact response bounds; secrets absent from GET, URLs, logs, public projections and browser storage.
- Derivation and AAD binding across workspace/run/operator/target/epoch; malformed base64, nonce/tag lengths, tag tampering and wrong-key refusal. Maximum text, AAD and whole-record bounds, including escaping-heavy request bodies.
- Actual page crypto and storage behavior: Unicode/multiline preservation, out-of-order async completions, edits during uncertain send, denied/quota-failed storage, stale record restoration, epoch rotation and opt-out/discard with pending identity retained.
- Rendered keyboard/focus/scroll behavior; full reload and same-origin server restart with fresh authentication; zero automatic send after restore; exactly one message and queued delivery after lost-response reconciliation; separate later receiver consumption remains truthful.
- Duplicated tabs, session replacement and independent browser storage. Do not infer safety from a single session digest; demonstrate refusal/idempotency and retained per-tab drafts.

Use the actual browser's platform crypto, not a test-only substitute. Missing required platform capability disables retention honestly and cannot pass the preservation gate. A requirement for shared or multi-browser drafts would reopen the storage decision. Inability to maintain the separate host secret/epoch lifecycle also reopens it. Neither justifies silently shrinking the promised reload/restart journey.
