## Contract boundary

The new namespace is `summon.workspace/v1`. Existing swarm/v1, room, council and deliberation validators are unchanged. No current dispatcher, coordinator or storage path imports this module. It performs no I/O, authentication, scheduling, launch, account selection, permission change, persistence or provider request.

**A validated evidence reference is a supplied claim, not verified evidence.** References contain an opaque ID and SHA-256 digest. A future trusted adapter/coordinator must resolve them, authenticate their source, check binding to the exact delivery/attempt, verify current scope and physical ownership, and establish successful durability before applying an event. A caller can construct a structurally valid fictional receipt. These validators never certify it. In particular, `authenticated_disposition`, `current_grant` and `physical_fence` are evidence-reference field names, not authentication primitives or trusted capability dictionaries. Arbitrary `auth_context` and unknown fields refuse.

Only canonical JSON dictionaries/lists/scalars are accepted. IDs follow the existing lowercase opaque 128-character convention; digests are lowercase SHA-256. Integers exclude booleans, floats, negative values and overflow. Unknown fields, invalid Unicode, unsupported enums and versions refuse. Every complete record is bounded to 48 KiB of canonical compact JSON encoded in UTF-8, including escaped text and structural overhead. This bound excludes framing/newline/storage overhead: integration must reserve actual persisted/transport bytes under R13, not assume this is a journal admission calculation. Private message content has a separate 4 KiB bound.

## Minimal records

| Record | Meaning and bindings |
| --- | --- |
| Goal | Workspace/run, goal ID/revision, objective, at most 16 observable criteria, constraints, active priority and unresolved decisions. This is a definition, not execution state. |
| Lane | Goal/revision, task and lane IDs, immutable task request digest, role, concrete outcome/scope, external authority reference, duration/attempt/context bounds, criterion IDs, return condition and escalation trigger. The authority reference must point to a separately verified permission/contact/spend envelope; budget numbers do not issue one. |
| Message | Logical message ID; source/destination task; goal/run; distinct sender and recipient instance/epoch; grant reference; stream/sequence; opaque private content reference, digest and byte count; optional correlation/reply/causation IDs. Bodies are not stored in these records. |
| Delivery | Separate delivery ID, logical message ID, recipient/grant, state/reason, optional frozen selection, certainty, inherited uncertainty and acknowledgement level. A selection binds task, claim, numbered attempt, owner generation, request/context digests, up to eight whole selected logical message IDs and optional turn ID. |
| Assessment | Supervisor identity claim; exact goal revision/task/lane; criterion results; bounded evidence links, limitations, HANDOFF, reason; typed priority disposition and proposed next decision. This does not mark coordinator tasks terminal or launch a successor. |

`validate_goal_binding` checks lane scope and assigned criterion coverage in an assessment. `criteria_satisfied` means the assessed assigned criteria are all met; it is not whole-goal completion when other lanes/criteria remain. The future conductor must check all required goal criteria and unresolved work independently. A met result must link supplied evidence, but neither the supervisor name nor fluent result authenticates it.

`validate_content` checks complete caller-supplied UTF-8 bytes against the logical message's byte count and digest without opening files. `validate_immutable_record` accepts identical duplicate goal/lane/message/assessment definitions and rejects conflicts. This slice has no goal-revision mutation API; a future explicit event must preserve revision history.

`validate_delivery_binding` is deliberately restricted to initial deliveries. A caller cannot invent `parent_delivery_id` to bypass recipient/grant equality. Linked deliveries use `validate_linked_delivery` with an actually resolved parent and disposition; the future store must validate the complete authoritative lineage back to the admitted logical message and enforce uniqueness. No standalone snapshot proves it has valid history.

## Delivery transitions

`validate_transition(before, after, evidence, supported_ack_levels=...)` checks only normative edges and preserves immutable bindings. It rejects all other state pairs, including same-state rewrite and terminal requeue. Idempotent event replay belongs to the coordinator's separate operation-key contract.

| Edge | Structurally required evidence references / extra claims |
| --- | --- |
| accepted -> queued | Durable admission reference. |
| queued -> included_in_attempt | Recorded selection and whole-message-fit references; freeze selection once. |
| included_in_attempt -> submission_started | Current grant, recipient/owner fence, capacity reservation, physical-attempt reservation and durable launch-intent references. Contact/spend/cleanup become unknown. |
| submission_started -> submitted | Adapter receipt plus named documented submission boundary; contact is claimed occurred, spend/cleanup are not settled. |
| submitted -> acknowledged | Separate acknowledgement receipt and matching supported level. Adapter capabilities default to no supported acknowledgements. Available schema levels are `adapter_received` and `recipient_received`; neither means model understanding. |
| included_in_attempt/submission_started -> not_submitted | No-contact receipt, cleanup-evidence reference and explicit boolean false for both provider contact and side effects. Missing/unknown/numeric false values refuse. Prior occurred contact or incurred spend contradicts this edge. |
| queued/included_in_attempt/submission_started/submitted -> held_for_recovery | Hold observation and a typed reason: native collision, recipient drift, revocation, contact uncertainty, cleanup uncertainty, incompatible fork, or content missing/mismatching/unavailable. Preserve selection, positive historical effect facts and unresolved uncertainty. |
| queued -> rejected/expired/cancelled | Validated refusal, expiry observation with checked time comparison, or authorized cancellation reference respectively. |
| held_for_recovery -> dead_lettered | Explicit authenticated-disposition reference; effect certainty and original attempt remain unchanged. |

Cleanup describes owned local resource status separately from provider contact. `not_started` means no local resource was started requiring cleanup; `complete` means cleanup is claimed complete and needs verified cleanup evidence. A child may have run locally and been cleaned up without contacting a provider. Proven no-contact can therefore retain `complete`; it cannot change completed cleanup to `not_started`, hide unknown cleanup, or substitute for a later physical fence.

`validate_linked_delivery` validates a new queued record while leaving the parent unchanged. Parent states eligible for linking are only `not_submitted`, `held_for_recovery` and `dead_lettered`. Each requires explicit disposition and remaining-authority references; held/dead-lettered parents additionally require a fresh attempt-grant reference matching a distinct child grant and a physical-fence reference. Recipient change additionally requires transfer-authority evidence. Logical message/run/workspace identity remains fixed. This function validates no network/session transfer and gives no permission to replay prior submitted effects.

A child's certainty concerns its own not-yet-attempted submission. Every unresolved contact/spend/cleanup dimension in the parent, plus earlier inherited uncertainty, must appear in the child's distinct `inherited_uncertainty` set. Linking and dead-letter bookkeeping never resolve those facts. Positive historical effects remain in the immutable parent. Integration must display and reconcile both lineage and current-attempt facts; child `not_attempted` cannot mean the logical message was never previously submitted.

## Preliminary pure replay and projection increment

`skills/summon/scripts/_workspace_state.py` now prepares the coordinator integration seam without activating it. Its focused no-I/O fixtures are `skills/summon/scripts/test_workspace_state.py`. No journal, sidecar, IPC, scheduler, provider, worker launch or second task-lifecycle store was added. The existing coordinator has not been changed to accept these events.

`apply_event(previous_projection, admitted_event, coordinator_view)` returns a detached projection or refuses without mutating its inputs. `replay` consumes ordered `(event, coordinator_view_at_that_position)` pairs. `project` takes a fresh coordinator view and uses its current task statuses. The input seam matches the relevant fields of `SwarmCoordinator.status()`: run ID and each task's ID, request digest, status, attempt count and active claim ID/generation. Integration should derive this view directly from the coordinator's in-memory reducer at that journal position; it must not call a fresh disk-loading status method inside every replay step or supply the final snapshot for all historical events.

The coordinator remains the sole writer and task/claim authority. After its normal replay applies an existing task event, it supplies the resulting task view to the next workspace event. Goal/lane definitions bind existing prepared task IDs and request digests. Workspace events contain no task-completion operation. Assessments retain a labeled historical observation of task status at their event position; current task status is always projected from the new coordinator view. A stale or invented caller-supplied view has no independent authority: authentication, ownership and truthful historical views remain integration obligations.

The exact new event envelope contains `event`, workspace protocol version, workspace/run IDs, semantic `operation_key`, `expected_revision` and bounded `payload`. Full envelope bytes count toward the 48 KiB structural limit. The initial `workspace_feature` event requires feature `goal_messages`, integer version 1 and expected revision zero. Subsequent supported events are:

- `workspace_goal_defined` and `workspace_lane_defined`: one initial goal revision and bounded prepared lane definitions. Explicit goal revision changes remain a later reviewed event; this increment does not overwrite goal history.
- `workspace_evidence_registered`: immutable evidence reference, category and existing lane task scope, with an existing delivery binding where applicable. Registration represents a prior trusted coordinator admission; it is not independent validation of an external artifact, receipt or permission grant.
- `workspace_assessed`: current goal/lane criterion coverage, registered scoped evidence, and a historical coordinator-status observation.
- `workspace_next_lane_selected`: distinct prepared target task, prior source-lane assessment and current goal revision. The target must be unattempted/pending; a repeated identical decision operation is a no-op, while another decision for that target refuses. Selecting it changes displayed priority only. A separate verified execution grant and coordinator claim are still mandatory.
- `workspace_message_admitted`: atomic logical-message/initial-delivery projection with existing source/destination lanes, a registered grant reference, ordered stream binding and resolved reply/causation IDs.
- `workspace_delivery_advanced`: resolves the current delivery and registered task/delivery-scoped proof references, then calls the protocol transition validator. Selection must match the coordinator's active claim, request, attempt and generation, and whole selected messages must have eligible recipient-bound deliveries.
- `workspace_delivery_linked`: resolves the actual parent, enforces one successor for that disposition lineage, resolves authority/fence references, and calls the separate linked-delivery validator. It never modifies the parent or clears inherited uncertainty.

The reducer's operation registry hashes the complete canonical event. Exact replay returns unchanged state, including when newer events have already been applied. Changed payload, scope, revision or event under the same key refuses. A duplicate entity under a different key also refuses. These rules suppress replay effects in this projection; they do not prove physical exactly-once submission or issue another attempt. Required launch-idempotency tests remain at the coordinator/adapter seam.

Selection's preliminary protocol field `owner_generation` is mapped specifically to the persisted claim's `lease_generation` fence in this bridge. It must not be populated from the transient coordinator journal-writer ownership generation, which changes independently between mutations. A fixture varies unrelated writer-generation metadata while preserving the claim fence. A clearer protocol field name requires a separately reviewed schema change; this reducer does not silently rename the existing contract.

Required predecessor handling is stream-scoped: an earlier logical message with a still-held leaf delivery blocks later inclusion in that stream. An earlier accepted, queued or included leaf also cannot be skipped: the selected context must contain the whole eligible prefix in stream order, and an already included predecessor must have the same frozen selection. Accepted-but-not-queued predecessors cannot be selected. A historical parent with a separately validated successor is not treated as the active leaf. All messages in this first contract are required; no caller-provided optional-message flag bypasses the rule. A different stream can remain eligible. Per-selection recipient eligibility and frozen context still apply independently. The facade must durably bind every selected delivery before contact; one per-delivery projection update is not atomic whole-attempt admission.

Proof roles have explicit allowed registered categories. Submission and acknowledgement receipts require `adapter_receipt`; arbitrary delivery-bound observations or artifacts cannot substitute. Grant, physical-fence, launch-intent, selection, expiry, cleanup and disposition roles likewise have explicit category sets. Category checking establishes only structural coherence, not authentication or evidence truth. Most proof references additionally bind the exact existing delivery; current/fresh/remaining/transfer grants and a new physical fence have their separately checked task-scoped roles.

Every linked child's `grant_ref` must itself resolve to the `grant` category, including successors of `not_submitted` parents where no fresh-attempt-grant proof field is required. A separate valid remaining-authority reference cannot make an artifact-category child reference into a grant.

Initial structural bounds are 2,048 distinct admitted operations, 16 lane definitions, 256 evidence references, 32 logical messages, 128 deliveries, 64 assessments and 64 decisions. Coordinator-view input has a 1,024-task cap matching the existing coordinator's `MAX_TASKS`; the active-worker limit remains a different policy. Exhaustion refuses before projection mutation and never prunes replay evidence. They are conservative fixture ceilings, not measured scale claims or R13 reserve arithmetic. Runtime capacity admission must account for combined coordinator/workspace history, required control/recovery obligations and actual serialized persisted bytes.

The fixtures demonstrate one goal with `main-1`, `side-1` and `main-2`, two assessment iterations and an idempotent causal next-lane decision. Historical input places main-one completion while the side lane is claimed; projection later follows the coordinator's current status without rewriting that observation. These are deterministic replay facts from supplied views, **not proof that real concurrent workers performed useful work**. The later owned-worker conductor demonstration must establish actual event ordering, execution grants and evidence acquisition.

Compatibility evidence is deliberately narrow: the unchanged legacy `SwarmCoordinator._apply_record` rejects the new feature event without changing its supplied in-memory state. This does not prove whole old-writer refusal before filesystem mutation: current `_mutation` acquires an owner before `_load` validates events. P1-C04's ownership/repair/pre-mutation compatibility gate remains open. Integration must also place the mandatory feature marker correctly relative to the existing unique leading `swarm_prepared` record and reject unsupported versions before mutation or repair. Adding this pure helper does not meet that gate.

The lead's selected integration direction is a versioned outer layout with a manifest and a structural managed-file-name directory guard, containing the inner coordinator state. Published outer entry points must make old commands refuse at their first `_fence_run_files` inspection, before acquisition or repair. That layout and its actual old-writer tests belong to the compatibility/coordinator lane; this pure increment implements neither and does not claim the gate passed.

HANDOFF for replay integration: review the pure reducer and coordinator-view seam, then attach it only through the existing coordinator's admitted-event/replay boundary after R13. Register evidence only after source resolution and verification; enforce channel and grant identity independently; derive historical views during replay; preserve immutable task terminal facts; and close old-writer, bounded-storage, claim-idempotency, crash and real simulated-conductor gates before describing this increment as an operational workspace.

## Preliminary owned-pipe synthetic transport

`skills/summon/scripts/_workspace_transport.py` and `test_workspace_transport.py` add a bounded transport fixture independently of coordinator activation. `OwnedFakeWorker` launches only the fixed receipt-producing worker in this module through the current Python executable, isolated mode and redirected standard pipes. Every launch uses shared `_spawn.popen_flags()`, `close_fds=True`, unbuffered pipes, a minimal environment and no shell. Bootstrap session key and challenge travel only through the dedicated owned stdin pipe, never argv, environment, journal, telemetry or diagnostic text. The child has no generic command execution or provider code; context remains payload data.

The connection contract is `summon.workspace.pipe/v1`. A four-byte length prefix bounds the complete JSON frame to 8 KiB; whole context separately has a 4 KiB UTF-8 bound. Reads handle short headers/bodies and refuse incomplete/oversized frames. HMAC authenticates connection nonce, direction, instance/epoch, workspace/run/task/grant binding, strictly increasing sequence and payload digest. Wrong binding, tamper, sequence reuse/gap, unsupported fields and malformed payload revoke the channel. Directions are independent; worker receipts authenticate back to the supervisor. These are issued-connection guarantees under the trusted OS-user/launcher model, not hostile-same-user process isolation, externally verified grants or served-model evidence.

The fixed worker returns separate `frame_received` and `acknowledged` frames after consuming and validating the complete input frame. The harness requires them in order and matches every message/delivery/attempt ID, context digest, complete request-frame digest and request sequence to its frozen pending request. Another correctly authenticated receipt cannot satisfy that request. One context may be in flight per connection; a second send refuses until both receipts arrive. No generic task completion or model-understanding claim follows from either response.

| Write observation | Meaning |
| --- | --- |
| `zero_write` | The unbuffered writer explicitly returned zero before any confirmed bytes. This alone is not a provider-level no-contact receipt or cleanup proof. |
| `partial_or_unknown` | Some bytes may have crossed, a write failed ambiguously, or its owner deadline elapsed. A first-write exception is also unknown. Revoke/clean up; never silently retry or call it proven zero. |
| `full_write` | The writer reported all frame bytes accepted. This does not establish recipient receipt, acknowledgement, durable state or provider contact. |

Bootstrap writes, context writes and response reads have positive finite bounded owner timeouts (default three seconds, allowed 0.01–30 seconds per I/O operation). A stalled owned write triggers channel revocation and fixed-child termination; it remains `partial_or_unknown` even if a late zero return arrives. Cleanup has its own bounded wait and reports uncertainty if it cannot confirm child exit. The low-level `read_frame`/`write_frame` helpers accept arbitrary stream objects and require the owning adapter to supply cancellation; the actual harness wraps them with owned deadlines. This is fixed-child cleanup only, not qualification of arbitrary provider process trees.

Actual Windows fixtures start two fake workers, verify separate authenticated receipt chains, reject a cross-channel frame while the other connection remains useful, and prove an unrelated deliberately inheritable pipe reaches EOF while both workers remain alive. They also cover partial pipe/disconnect, frame tamper/replay, complete Unicode bounds, receipt correlation, stalled write, invalid deadlines and hidden-launch configuration. Keys are volatile; closing or replacing the supervisor revokes its channel objects and terminates owned children. A replacement gets a new key/nonce and an explicitly supplied new epoch. Durable grant revocation, restart recovery, linked pending-delivery disposition and grant admission still belong to coordinator integration. No reconnect or native-session attachment is implemented.

HANDOFF for transport integration: freeze and independently review this synthetic transport, then connect it to durable-before-write selection/intent and verified receipt events through the existing coordinator. The current two-worker test proves owned connection behavior, not the complete two-iteration conductor demonstration, durable worker authorization, hostile-user isolation or live-provider readiness. Do not launch this harness automatically from a replayed message or assessment.

## Bounded draft correction following FABLE-WORKSPACE-02

The assessment's new `affected_task_ids` field is required, nonempty, unique and bounded to 16 opaque task IDs for `hold_affected_lane` and `promote_issue_to_priority`. These reasons preserve the frozen attempt and existing contact/spend/cleanup facts. ## Coordinator admission and finite settlement increment

This increment supersedes the earlier pure-helper integration status above. The existing coordinator now validates and replays ordinary workspace wrappers and one composite `workspace_turn_admitted` through its sole journal, normal owner/prefix reconciliation, exact frozen-byte append, and finite reserve. Its central capability contract advertises the nine ordinary workspace event classes and atomic claim/selection. This is a trusted-host, provider-inert integration boundary, not live-provider certification, worker authentication, a new release, or completion of the conductor demonstration.

Atomic payloads require `evidence_by_delivery`: its exact keys are the 1–8 unique `selected_delivery_ids`. Every map contains `current_grant`, `recipient_owner_fence`, `capacity_reservation`, `physical_attempt_reservation`, `selection_record`, and `whole_message_fit`; an optional already-observed `durable_launch_intent` remains structurally supported. Each current-grant reference matches the payload and delivery grant. Registered categories, task scope and exact delivery bindings remain mandatory. Shared `evidence` maps refuse even for one delivery. This is an unreleased draft correction; no shipped 3.4 record is migrated, rewritten, or silently converted.

The base derives workspace state from the same reconciled journal prefix under its mutation owner, calls the trusted host grant resolver there, and constructs a detached prospective claim. Canonical replay freezes all selected deliveries with that claim in the same composite append. It captures the lease deadline inside the transaction. Identical committed-operation retries return the original response before new-grant checks; they do not issue another launch or claim. Frozen selection, stream prefix, linked-recipient eligibility, goal revision and sticky target holds are rechecked structurally. Historical wrapper replay uses its persisted observation time; current status uses the live clock.

Evidence registration optionally carries `settlement_for = {delivery_id, target_state, role}`. It allocates one already-obtained, source-verified reference to a required proof role for a reachable delivery target. Category, task and delivery must agree. The reference is immutable per slot: exact registration replay gives no further capacity credit; conflicting, irrelevant or newly allocated already-consumed slots refuse. The transition must use the allocated reference. This metadata is reservation bookkeeping, never a grant, simulated receipt, authorization, or proof of future work. Untagged preparation and unrelated evidence use ordinary capacity.

Capacity reserves every remaining reachable delivery transition plus each unfilled required evidence-registration slot. Complete evidence-wrapper cost comes from the journal encoder; transition wrappers retain their full envelope bound. A fulfilled registration consumes its own allowance, and a transition consumes its event allowance and deterministically releases unreachable alternatives. Evidence/operation registry ceilings also preserve these pending slots. Claim settlement and renewal reserves remain separate. Linked retry adds a fresh child budget without rewriting the parent's effects. An additional unresolved-effects tail survives terminal acknowledgment or dead-letter disposition whenever contact, spend or cleanup uncertainty remains.

`close()` and the central close/replay paths refuse unresolved delivery obligations. Finished coordinator tasks cannot refund them. Status adds workspace delivery/unsettled counts, uncertain dimensions and `closure_ready`; all-terminal tasks with outstanding deliveries report `settlement_required`, while individual task terminal facts remain unchanged. The existing acknowledgment path does not resolve unknown spend/cleanup: an explicit separately reviewed effect-resolution operation is still needed for that normal-close journey. A clean, proven no-contact disposition can close through its existing legal path.

Verification for this increment: 138 focused coordinator/admission/replay tests; six exact-capacity acceptance methods plus three boundary subtests independently passed without source drift. Those fixtures obtain new evidence after admission, cover launch/receipt/acknowledgment and held/disposition paths, reject unrelated or duplicated credit, and refuse close until a clean legal disposition. A separate frozen gate passed 57 R13/runtime tests plus 52 subtests; the actual two-message base/facade resolver path also passed. Public conductor and live-provider claims require their own subsequent evidence.

## Explicit fixed-worker effects increment

The separate `workspace_effects_resolved` event implements the narrow contract in `docs/planning/P1_EFFECT_RESOLUTION_CONTRACT.md`. It can resolve only an acknowledged original fixed-worker delivery, without inherited uncertainty or a linked parent. Its two registered, task/delivery-bound roles are `fixed_execution_scope` (`observation`) and `owned_child_cleanup` (`fence`). The pure reducer validates their references and the immutable delivery relationship; the trusted runtime must independently verify actual launcher-issued source observations under the same mutation. Caller JSON, a digest, a simulated flag or a grant resolver alone cannot establish those observations.

The virtual `effects_resolved` reservation target is not a delivery lifecycle state. Before launch, an eligible path reaching acknowledgment reserves a distinct resolution wrapper plus those two registration slots, in addition to its ordinary uncertainty tail. Evidence registration consumes only its matching slot. Explicit resolution consumes its own event allowance; a branch unable to reach acknowledgment releases unreachable resolution slots while retaining unresolved effects. Provider histories and linked/inherited effects are ineligible.

The successful operation preserves occurred contact, acknowledgment, recipient, grant, selection and all prior receipt/history records. It changes only unknown spend/cleanup to `not_incurred`/`complete`, retaining `resolution_kind=fixed_worker_fixture/v1` and `qualification=simulated` in the projection. Task completion remains a separate coordinator fact. Duplicate operation replay cannot mint additional budget. Run closure becomes eligible only when both task and delivery obligations are actually settled. Structural exact-cap fixtures cover this sequence; actual-child provenance and complete conductor acceptance remain separate runtime/demo gates.

The central base contract now includes this tenth ordinary event after synchronized runtime integration. The affected coordinator/admission/replay suites plus original atomic-capacity and new effect-capacity suites passed 147 tests and 11 subtests. `tests/test_workspace_effect_capacity.py` reuses the frozen earlier fixture helpers without modifying their assertions. It verifies separately reserved late source registrations, resolution, duplicate no-credit replay and closure under the same calibrated cap, plus unchanged journals/reserves on invalid category, task, delivery, reference, selection or qualification. These synthetic-reference fixtures establish the journal contract; they do not substitute for the actual-child provenance gate.
